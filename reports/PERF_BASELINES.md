# Perf Baselines — Rack, Grid, Clip

What the three heavy surfaces cost, on both sides of the IPC boundary,
and what the CI gate will let them cost before it fails.

Measured 2026-05-21 on headless Linux: 4 cores, 15 GB RAM, rustc 1.98.0,
node v23.8.0, jsdom via vitest. **The host was shared** — other agents
were compiling throughout — so treat every figure as ±40 % and the gates,
not the figures, as the contract.

## Where the suites live

| Surface | UI rendering (vitest/jsdom) | Audio rendering (cargo, release) |
|---|---|---|
| Rack | `app/tests/RackPerf.test.tsx` | `crates/dj-engine/tests/perf_ui/rack.rs` |
| Grid | `app/tests/GridPerf.test.tsx` (last describe) | `crates/dj-engine/tests/perf_ui/grid.rs` |
| Clip | `app/tests/ClipPerf.test.tsx` | `crates/dj-engine/tests/perf_ui/clip.rs` |

Shared harnesses: `app/tests/perfHarness.ts` (calibration, budgets,
scaling) and `crates/dj-engine/tests/perf_ui/bench.rs` (throughput,
scaling). The frontend stage timings come from `app/src/perf.ts`, which
the dev stress HUD (`?stress=48`) also displays live.

Fixtures are generated by the tests — synthetic patches, arrangements and
tones. Nothing large is committed.

## Running them

```sh
cd app && npm run test:perf          # UI: Rack + Grid + Clip
DJ_PERF_HEAVY=1 npm run test:perf    # ...on the CI perf job's fixtures

cargo test -p dj-engine --release --test perf_m4 perf_ui -- --test-threads=1 --nocapture
DJ_PERF_HEAVY=1 cargo test -p dj-engine --release --test perf_m4 perf_ui -- --test-threads=1 --nocapture
```

`DJ_PERF_HEAVY=1` multiplies every fixture (16→48 modules, 128→384 beats,
240k→720k peaks, 62→202 engine modules, 60 s→300 s of audio). Normal size
is what runs on every push; heavy is the `perf` CI job, on main only.

| rack telemetry tick | 4 polls at 10 Hz | 0 cable re-measures | must be 0 | same | 0 | must be 0 |
| grid open | 50 rows × 128 beats | 1.1 s | 6 s | 100 × 384 | 5.6 s | 20 s |
| grid flick (30 scroll events) | 8 rows × 512 beats | 0.40 s | ≤ ×1.6 at ×2 beats | 8 × 1024 | 0.59 s | ≤ ×1.6 |
| grid zoom burst (30 wheel events) | 50 rows × 128 beats | 0.31 s | 1.2 s | 100 × 384 | 1.4 s | 3 s |
| clip open | 600 s track, 240k peaks | 0.08 s | 1 s | 1800 s, 720k peaks | 0.18 s | 3 s |
| clip selection drag (20 moves) | 240k peaks | 0.23 s, 19 renders | 1.5 s, ≤ 30 renders | 720k peaks | 0.30 s, 19 | 4 s |
| clip automation (20 breakpoints) | 240k peaks | 0.20 s | 1.5 s | 720k peaks | 0.31 s | 4 s |

Whole-suite wall clock: 44 s normal, 82 s heavy (4 cores, shared host).

Budgets are multiplied by a **calibration factor** measured at the start
of each file (a fixed arithmetic workload against a reference time), so a
box half as fast gets budgets twice as large. On the shared host the
factor swung between ×1.0 and ×3.9 during a full `npm test`.

### Where the UI time goes (instrumented stages)

- `rack.wireMeasure` — 21 ms per mount over 3 measures at 16 modules.
  Was **529 ms** before this work: the overlay looked each jack socket up
  with its own `querySelector`, i.e. quadratic in patch size. Now one
  pass builds a socket map.
- `waveform.peaksPath` — 70 ms over 127 calls during a selection drag,
  about a third of the drag. The dearest thing on the Clip page.
- `clip.programPeaks` — 33 ms over 63 calls while dropping 20 automation
  breakpoints (every breakpoint recuts the peaks).
- `grid.gridColumns` — microseconds; not a bottleneck, instrumented for
  completeness.

## Audio rendering (release, ×realtime)

| Bench | Normal fixture | Measured | Heavy fixture | Measured | Floor |
|---|---|---|---|---|---|
| rack render | 62 modules, 10 s | 3.2× | 202 modules, 30 s | 1.0–1.1× | 1.2× / 0.25× |
| rack build | 62 modules | 4.3 s (~70 ms/module) | 202 modules | 10.9 s (~54 ms/module) | < 200 ms/module |
| grid track-fx row | 6-module rack, 20 s | 18.6× | 60 s | 33.5× | 3× |
| grid bounce | 8 rows × 4 s | 9.2× | 24 rows × 4 s | 8.1× | 2× |
| clip render | 60 s, 24 regions | 29.9× | 300 s, 96 regions | 31.7× | 3× |

Whole-suite wall clock: 57 s normal, 119 s heavy (release, `--test-threads=1`).

### Where the audio time goes

- **Clip**: the warp is 86 % of a render (7.6 s of a 9.1 s heavy render);
  EQ, level and splice together are under 15 %. `ClipRenderProfile`.
- **Grid**: building a row's rack is ~320 ms (six wasm instantiations)
  against ~730 ms to render 20 s through it — so on a **fifty-row set of
  short rows the build is 70 % of the whole bounce**. `TrackFxProfile`.
  A rack-instance cache is the obvious win if that ever hurts.
- **Rack**: 202 modules render at ~1.1× realtime on one core, so a patch
  that size is at the edge of playable. Cost is linear-ish in the module
  count (×2.5 for ×2 modules at 100+ modules).

## The CI gate

- Every push: `frontend` runs `npm test`, which ends with `npm run
  test:perf` (normal fixtures); `stress` runs `--test perf_m4`, which now
  includes `perf_ui` (normal fixtures).
- Pushes to main: the `perf` job re-runs both at heavy size.

A failure prints `PERF REGRESSION` with the measured figure, the
threshold and a pointer here.

## Updating a baseline

Thresholds are deliberately loose — several times the measured cost — so
a failure means something real. Before moving one:

1. Re-run the bench on a quiet machine (`--test-threads=1`, nothing else
   building). Compare against the table above, not against your memory.
2. If the cost is a deliberate trade (a new stage, a better-sounding but
   dearer render), move the threshold in the test, update this table in
   the same commit, and say in the commit message what was bought.
3. If it is not deliberate, the instrumented stage names above are where
   to look: the profile line each bench prints attributes the time
   without a profiler.

Do NOT tighten a threshold to just above the current measurement. These
run on shared CI runners; a gate that fails for noise gets ignored, and
an ignored gate is worse than none.
